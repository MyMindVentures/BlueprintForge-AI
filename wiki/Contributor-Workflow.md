# Contributor Workflow

## Standard workflow

1. Fork the repo.
2. Create a feature branch.
3. Pick or claim an issue.
4. Build a focused improvement.
5. Test locally.
6. Open a pull request.
7. Add screenshots for UI work.
8. Respond to review feedback.

---

## Recommended branch names

```txt
feature/premium-app-shell
feature/builder-profile
feature/company-bid-room
feature/revenue-recoupment
ui/object-docs-canvas
fix/mobile-navigation
```

---

## PR expectations

A pull request should include:

- what changed
- why it matters
- screenshots or video for UI work
- mobile/tablet notes
- known limitations
- linked issue

---

## Good contribution scope

Good PRs are focused.

Avoid PRs that change many unrelated parts of the app at once.

---

## Safe data rule

Use mock data only.

Do not include:

- private company data
- real bid data
- confidential app ideas
- private legal text
- API keys
- credentials

---

## Contributor recognition

Contributors may be recognized through public contribution history, trusted contributor levels, and future invitations to deeper collaborations.
